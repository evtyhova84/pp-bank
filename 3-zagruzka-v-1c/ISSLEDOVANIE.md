# Часть 3 — загрузка распознанных счетов в 1С

Дата разбора: 2026-08-27.

## Главное отличие от части 1

В части 1 нам повезло: `1CClientBankExchange` — **утверждённый открытый формат**,
один на всю страну. Здесь такого нет.

**«Счёт на оплату» — неформализованный документ.** ФНС утвердила XML-форматы для
счёта-фактуры, УПД, ТОРГ-12 и акта, но не для счёта на оплату. Универсального XML,
который любая 1С поймёт из коробки как «счёт», не существует.

Поэтому вопрос не «какой формат», а «каким каналом заводить документ в 1С».
Реальных каналов три.

---

## Канал A. OData — прямая запись в базу (рекомендуется)

**Стандартный интерфейс OData** — штатный REST-интерфейс платформы 1С, есть с версии 8.3.5.
Реализована спецификация OData 3.0, ответы в Atom/XML или JSON.

Умеет: чтение (GET), **создание объектов (POST)**, обновление (PATCH/PUT), удаление (DELETE),
**проведение документов**.

Обычно требует публикации на веб-сервере (IIS/Apache) и разрешения состава объектов
через `УстановитьСоставСтандартногоИнтерфейсаOData()`. **Но у нас 42Clouds — см. ниже,
там это уже сделано.**

Плюс: никаких файлов, документ появляется в базе сразу, можно сверить и не проводить.
Минус: работает только с онлайн-базой, нужна учётка и сеть.

## Канал B. EnterpriseData — XML-файл, который 1С забирает из папки сама

**EnterpriseData** — универсальный формат обмена данными «1С», XML. Версия 1.0.1
описывает **94 типа бизнес-сущностей** (документы, справочники: контрагенты, договоры и т.д.).

Каналы обмена: **файловый обмен через каталог**, FTP, электронная почта, веб-сервис.
На стороне 1С регистрируется уникальный код стороннего приложения; синхронизация
идёт **по расписанию** или вручную.

Вот это и есть прямой ответ на «грузить автоматически из папки»: наш скрипт кладёт XML
в каталог, 1С по регламентному заданию его забирает. Никакого стороннего сервиса не нужно.

Плюс: работает и с локальной базой без веб-публикации; формат официальный.
Минус: настройка синхронизации на стороне 1С; **состав объектов надо проверить** —
есть ли в формате нужный нам документ, смотрится в самой базе
(Администрирование → Синхронизация данных → состав отправляемых/получаемых данных).

## Канал C. ЭДО-XML (форматы ФНС) — не наш случай

Именно этим путём работает сервис 42Clouds «Загрузка документов поступления из файла XML»:
принимает XML, выгруженный из систем ЭДО (в описании упомянут Контур.Диадок),
создаёт **«Поступление товаров и услуг»** и «Поступление денежных документов».

Не подходит по двум причинам: это про накладные и УПД, а не про счёт на оплату,
и загрузка **интерактивная** — пользователь выбирает файлы руками, расписания нет.

## 42Clouds: что нашлось

### OData включён автоматически

По техдокументации 42Clouds интерфейс OData **включён автоматически для всех баз**,
отдельная услуга или веб-публикация не требуется.

- Адрес: `https://bp.42clouds.com/<база>/<зона>/odata/standard.odata/`
- Пример: `.../odata/standard.odata/Catalog_Контрагенты`
- Аутентификация: HTTP Basic. Рекомендуется **отдельный служебный пользователь**,
  создаётся в *Администрирование → Синхронизация данных → Настройки стандартного
  интерфейса OData*. Существующие учётки использовать не советуют.

⚠️ Проверить в своей панели — документация может отставать от тарифов.

### В Маркет42 под нашу задачу ничего нет

Категория «Интеграция» на 2026-08-27: журнал-дерево документов, УЭТ:М.Видео,
просмотр элементов формы, гибкий поиск, группировщик объектов, обработка реквизитов,
менеджер доп. реквизитов, **выгрузка УПД в XML**, **intoai** (ИИ-аудит первички
и автопроведение), групповое создание документов.

Загрузчики есть только маркетплейсные (WB, Ozon, М.Видео, Аптеки+) и прайс-листы из Excel.
**Покупать нечего** — OData закрывает задачу лучше и бесплатно.

Косвенно полезное: `intoai` — ИИ-аудит первичных документов. Прямой конкурент нашей
части 2 в узкой нише, стоит посмотреть, что он умеет.

## Предлагаемая архитектура части 3

Один источник данных, три выхода — контракт из CLAUDE.md уже подходит без изменений:

```
Часть 2 (распознавание)
        │
        ▼
   структура счёта
     ├──► Часть 1: TXT для клиент-банка   (готово)
     └──► Часть 3: документ в 1С
            ├── режим odata     — POST в базу
            └── режим enterprisedata — XML в папку обмена
```

## Обязательные требования к части 3

1. **Идемпотентность.** Тот же ключ счёта, что и в нумерации платёжек
   (`Invoice.identity`): повторный запуск не должен плодить дубли документов в базе.
   Журнал «этот счёт уже заведён как документ такой-то» — по образцу `reestr-nomerov.json`.
2. **Не проводить по умолчанию.** Документ создаётся непроведённым, бухгалтер смотрит
   и проводит сам. Проведение — явный флаг.
3. **Боевая база — не песочница.** Отдельный служебный пользователь, права минимальные,
   сначала обкатка на копии.

## Что нужно выяснить

- [ ] какая конфигурация 1С (БП 3.0 / УТ / КА) — от неё зависят имена объектов;
- [ ] какой документ заводить: «Счёт от поставщика» или сразу «Поступление»;
- [ ] точное имя объекта в OData — смотрится одним запросом к `$metadata`
      публикуемой базы, гадать не нужно;
- [ ] есть ли нужный документ в составе EnterpriseData для этой конфигурации.
