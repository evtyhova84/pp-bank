## 1. Что делает система

На вход — счета на оплату от поставщиков (PDF, скан, фото). На выходе — один
текстовый файл `1c_to_kl.txt` формата `1CClientBankExchange`, который бухгалтер
сам загружает в клиент-банк.

Три жёстких правила, из которых следует всё остальное:

- **Ничего не уходит в банк автоматически.** Итог работы — файл. Загружает
  его человек.
- **Реквизиты не додумываются.** Сумма, ИНН, КПП, БИК, номер счёта нечитаемы —
  счёт идёт человеку, а не в файл с догадкой.
- **Реквизиты плательщика — данные, а не код.** В исходниках нет ни одной
  конкретной организации: инструмент рассчитан на передачу сторонним компаниям.

Ключевой приём всей системы: **реквизиты счёта самопроверяемы.** У ИНН, БИК,
расчётного и корреспондентского счёта есть контрольные суммы, ставка НДС
сходится с суммами. Пять независимых проверок на документ — ошибка в одной
цифре почти наверняка их ломает. Поэтому кривое распознавание уходит человеку,
а не в банк, и это работает без всякой модели.

## 2. Архитектура

```
                    ┌──────────────────────────────┐
                    │  Часть 2: распознавание      │
   PDF / скан ─────►│  2-raspoznavanie/parser/     │
                    │  текстовый слой или OCR      │
                    └──────────────┬───────────────┘
                                   │  контракт данных (dict)
                    ┌──────────────▼───────────────┐
                    │  Часть 1: генератор          │
                    │  1-vygruzka-v-bank/generator │──► 1c_to_kl.txt
                    │  проверки + нумерация        │
                    └──────────────────────────────┘
                                   ▲
                    ┌──────────────┴───────────────┐
                    │  Часть 4: сервис (servis/)   │
                    │  веб, роли, справочники,     │
                    │  пачки, журнал нумерации     │
                    └──────────────────────────────┘
```

Части 1 и 2 не знают друг о друге ничего, кроме контракта данных. Часть 1
не зависит от распознавания вообще: ей всё равно, откуда пришла структура.

**Сервис логику частей 1 и 2 не дублирует, а вызывает.** Мост — единственный
файл [servis/app/yadro.py](servis/app/yadro.py): папки частей начинаются
с цифры (`1-vygruzka-v-bank`), импортировать их как пакеты нельзя, поэтому
они подключаются через `sys.path`. Так же устроен и `konveyer.py`.

Ровно два узла в сервисе заменены на свои:

| Узел | В частях 1–2 | В сервисе | Почему |
|---|---|---|---|
| Журнал нумерации | JSON-файл, `generator/numbering.py` | таблицы SQLite, `app/nomera.py` | на сервере сотрудников несколько, два одновременных «Сформировать» обязаны получить разные номера |
| Справочник плательщиков | JSON-файлы | таблицы `payers` / `payer_accounts` | нужен интерфейс, а не редактирование файлов |

Точки входа:

| Файл | Что запускает |
|---|---|
| `python -m generator` | только генератор файла для банка |
| `python -m parser` | только распознавание папки со счетами → JSON |
| `python konveyer.py` | сквозной прогон: папка счетов → файл для банка |
| `python -m servis` | веб-сервис (uvicorn, по умолчанию `127.0.0.1:8000`) |
| `zapusk.bat` → `zapusk.pyw` | окно с тремя кнопками, без консоли |

## 3. Контракт данных

Часть 2 отдаёт, часть 1 принимает — обычный `dict` (или JSON-массив таких).

### Получатель платежа

| Поле | Смысл |
|---|---|
| `recipient_name` | краткое наименование — идёт в поле «Получатель» |
| `recipient_full` | полное наименование |
| `recipient_inn` | ИНН, 10 знаков у ООО, 12 у ИП и физлица |
| `recipient_kpp` | КПП, 9 знаков; у ИП и физлица не бывает |
| `recipient_account` | расчётный счёт, 20 знаков |
| `recipient_bank_name` | название банка |
| `recipient_bank_city` | город банка — в файле это отдельное поле |
| `recipient_bic` | БИК, 9 знаков |
| `recipient_corr_account` | корреспондентский счёт, 20 знаков, префикс `301` |

### Платёж

| Поле | Смысл |
|---|---|
| `invoice_number` | номер счёта поставщика (может быть с буквами: `1/ПМ`) |
| `invoice_date` | дата счёта |
| `total_amount` | сумма к оплате |
| `vat_rate`, `vat_amount` | ставка и сумма НДС |
| `vat_status` | `included` / `none` / `unknown` — см. ниже |
| `payment_purpose` | готовое назначение платежа; имеет приоритет |
| `payment_description` | «за что платим»: наименования позиций через «; », без цен и количеств |

### Три поля, которые стоят отдельного объяснения

**`vat_status`** — различие между «НДС нет» и «про НДС не сказано»:

- `included` — НДС выделен, есть сумма и ставка;
- `none` — в счёте прямо написано «Без НДС», «Сумма НДС: 0,00», «Режим НО: НПД»;
- `unknown` — не нашли и про отсутствие не сказано.

Без этого различия бухгалтер получает предупреждение на каждом счёте ИП на УСН
и перестаёт читать предупреждения вообще. Счёт с `unknown` в файл не уходит:
иначе в назначении платежа окажется «Без НДС» наугад, а это удар по вычету.

**`recipient_kind`** — `org` / `ip` / `self_employed` / `person`. Физлицу
(самозанятому в том числе) генератор ставит код вида дохода `1` в поле 20
(`КодНазПлатежа`, обязателен с 01.06.2020 по 229-ФЗ ст. 8 ч. 5.1) и не пишет
КПП. Организациям и ИП поле пустое — иначе банк примет платёж за выплату
физлицу и начнёт считать удержания. Признаки и банковские правила разобраны
в [PRAVILA-samozanyatye.md](PRAVILA-samozanyatye.md).

**Служебные поля с подчёркиванием** в платёжку не идут, ими пользуется
сервис: `_buyer_inn`, `_buyer_name`, `_buyer_kpp` (на кого выставлен счёт),
`_name_unreliable` (наименование распознано ненадёжно), `_vat_iz_spravochnika`
(НДС подставлен из истории получателя).

### Пары «число + строка»

Каждая распознанная сумма хранится парой: `total_amount` и `total_amount_str`,
`vat_amount` / `vat_amount_str`, `vat_rate` / `vat_rate_str`. Оригинальная
строка из счёта не теряется при ошибке разбора числа.

## 4. Часть 1 — выгрузка в банк

Каталог `1-vygruzka-v-bank/`. Зависимостей нет, нужен только Python 3.10+.

| Файл | Отвечает за |
|---|---|
| `generator/models.py` | входные данные: `Payer`, `Invoice`, `BankProfile`, `PaymentOrder`; разбор дат и сумм |
| `generator/validate.py` | контрольные суммы ИНН и счетов, ограничения ЦБ на номер, проверка кодировки |
| `generator/numbering.py` | счётчики и журнал закреплённых номеров (`NumberRegistry`) |
| `generator/export.py` | сборка файла (`Exporter`), назначение платежа |
| `generator/cli.py` | командный интерфейс |
| `profili-bankov/` | различия между банками |

### 4.1. Формат файла

Полный разбор спецификации по пунктам —
[FORMAT-1CClientBankExchange.md](1-vygruzka-v-bank/FORMAT-1CClientBankExchange.md).
Коротко:

- открытый стандарт «1С» для обмена с системами «Клиент банка», простой текст
  `ключ=значение`;
- имя `1c_to_kl.txt` — направление «из 1С в банк»;
- **кодировка windows-1251** (`Кодировка=Windows`) или cp866 (`DOS`),
  переводы строк **CRLF**. UTF-8 банк не примет — это самая частая причина
  отказа импорта;
- версия формата 1.02 по умолчанию: 1.03 актуальна, но часть банков на ней
  капризничает;
- значение всегда в одну строку, суммы с точкой и двумя знаками, даты `дд.мм.гггг`;
- структура: строка-маркер `1CClientBankExchange` без «=», шапка, N секций
  `СекцияДокумент=Платежное поручение … КонецДокумента`, `КонецФайла`;
- секции выписки (`СекцияРасчСчет`) в нашем файле нет — она только для
  направления «из банка в 1С».

`НазначениеПлатежа` выводится дважды — и в `НазначениеПлатежа1`: в реальных
файлах они дублируются, и часть банков иначе теряет назначение.

### 4.2. Профили банков

Универсальность даёт не «один файл на всех», а одно ядро генератора плюс тонкие
профили в `profili-bankov/*.json`. Профиль выбирается полем `bank_profile`
у плательщика или флагом `--profile`.

| Параметр | Что решает | По умолчанию |
|---|---|---|
| `format_version` | версия формата | `1.02` |
| `encoding` | `Windows` → cp1251, `DOS` → cp866 | `Windows` |
| `sender` / `receiver` | что писать в шапке | `scheta-platezhki` / пусто |
| `emit_empty_fields` | выводить пустые необязательные строки | `false` |
| `uin_when_absent` | что писать в `Код` (УИН), когда его нет | `0` |
| `purpose_max_length` | предел назначения платежа | `210` |
| `payment_kind` | `ВидПлатежа`: пусто = электронно | пусто |
| `payment_type` | `ВидОплаты` | `01` |
| `priority` | `Очередность` | `5` |
| `duplicate_purpose_line` | дублировать назначение | `true` |
| `income_code_for_persons` | `КодНазПлатежа` физлицу | `1` |

Новый банк = копия `default.json` с другим `name`. Придирки выясняются пробной
загрузкой, чек-лист — п. 8 спецификации формата.

### 4.3. Проверки до записи файла

`validate.py`. Если есть хоть одна ошибка уровня `error`, поднимается
`ExportError` и **файл не пишется вообще** — не «пишется частично», не
«пишется с предупреждением».

Что проверяется:

- **ИНН** — контрольная сумма по алгоритму ФНС, для 10 и для 12 знаков;
- **счёт** — контрольный ключ по алгоритму ЦБ РФ: к счёту приписывается
  префикс (три последних знака БИК для расчётного, `0` + знаки 5–6 БИК для
  корреспондентского), сумма произведений на веса `7,1,3` должна делиться на 10;
- **КПП** — 9 знаков, знаки 5–6 могут быть буквами;
- **БИК** — 9 цифр;
- **номер платёжки** — ограничения ЦБ на поле 3: только цифры, не больше
  6 знаков, не ноль, три последних разряда ≠ `000`;
- **кодируемость** — весь текст файла проверяется на кодировку профиля
  посимвольно, до записи;
- **физлицо** — ИНН обязан быть из 12 знаков, КПП не должно быть вовсе
  (чужой КПП в платёжке физлицу — это КПП покупателя, распознанный не там,
  и банк такую платёжку вернёт);
- **предупреждения** (не блокируют): сумма НДС не распознана, номер счёта
  не найден, счёт встречается в пачке дважды, у плательщика не указан город банка.

### 4.4. Нумерация платёжных поручений

Решение целиком — [RESHENIE-numeratsiya.md](1-vygruzka-v-bank/RESHENIE-numeratsiya.md).
Главный риск не банк, а **обратная загрузка выписки в 1С**: 1С сопоставляет
строку выписки со своим документом по номеру, дате, сумме и счёту, и если наши
номера попадут в диапазон, где 1С нумерует свои платёжки, получатся дубли
документов или привязка платежа не к тому документу.

Принятое решение:

- выделенный верхний диапазон, по умолчанию **с 900001** (1С нумерует свои
  платёжки с единицы, это сотни в год);
- счётчик по ключу **(плательщик, расчётный счёт, год)**, обнуление 1 января;
- стартовый номер — настройка организации (`numbering_start`), не константа
  в коде: если 1С по счёту не ведётся, можно ставить `1`;
- запрещённые ЦБ номера (`X00000`) **перешагиваются**;
- **номер присваивается в момент выгрузки, а не распознавания** — иначе счета,
  полежавшие в системе, съедят номера, уже ушедшие в банк другой пачкой;
- **повторная выгрузка той же пачки даёт те же номера.** Номер закрепляется
  за счётом навсегда. Иначе двойное нажатие «Сформировать» даёт два файла
  с разными номерами на одни платежи — прямой путь к двойной оплате.

Ключ счёта (`Invoice.identity`) — склейка: id плательщика, его расчётный счёт,
ИНН получателя, счёт получателя, номер и дата счёта, сумма. По нему же
работает ответ на вопрос «этот счёт уже оплачивали?» (`already_paid`).

Отвергнутые варианты (буквенный префикс, нумерация с 1 каждый день, чтение
последнего номера из 1С, случайный номер) и причины отказа перечислены
в самом решении.

### 4.5. Назначение платежа

`export.py`, функции `build_purpose` и `fit_description`.

Готовый текст в `payment_purpose` имеет приоритет и просто обрезается
по пределу. Иначе назначение собирается по шаблону:

```
Оплата по счету № {номер} от {дата} за {описание}. В т.ч. НДС {ставка}% - {сумма} руб.
```

Без НДС хвост — « Без НДС.», без ставки — « В т.ч. НДС - {сумма} руб.»

**Обрезать назначение с конца нельзя**: банк и получатель смотрят именно
на сумму НДС. Поэтому в предел (210 знаков) ужимается описание, а хвост
про НДС уцелевает всегда. Правила ужатия:

- всё влезло — позиции перечисляются через запятую;
- не влезло, но у позиций есть общее начало хотя бы из двух слов — берётся
  оно: шесть «Заправка картриджа Kyocera 3253ci черн.» превращаются
  в «заправка картриджа Kyocera (6 позиций)» (склонение слова «позиция»
  считается по русским правилам);
- иначе перечисляется, сколько влезло, и добавляется «и др.»;
- одна длинная позиция обрезается по границе слова, без висящей запятой
  и без предлога на конце.

Первое слово описания с заглавной буквы («Услуги») после «за» пишется
со строчной; аббревиатуры и марки не трогаются.

Отдельно — `sanitize()`: типографские символы, которых нет в cp1251
(неразрывный пробел, тире, кавычки-ёлочки, многоточие, BOM), заменяются
на ближайшие допустимые, значение сводится в одну строку.

## 5. Часть 2 — распознавание счетов

Каталог `2-raspoznavanie/`. Слой **2а — шапка счёта**: реквизиты получателя,
номер и дата, суммы, НДС. Этого достаточно для платёжки — у платёжного
поручения нет табличной части. Слой 2б (позиции и сопоставление с номенклатурой
1С) не реализован и для платёжек не нужен; разбор задачи —
[NOMENKLATURA.md](2-raspoznavanie/NOMENKLATURA.md).

| Файл | Отвечает за |
|---|---|
| `parser/rows.py` | извлечение текста из PDF и картинок в единый вид |
| `parser/ocr.py` | два локальных движка распознавания картинок |
| `parser/ocr_repair.py` | починка цифр после OCR |
| `parser/fields.py` | поиск полей по меткам и признакам |
| `parser/items.py` | наименования позиций для «за что платим» |
| `parser/norm.py` | нормализация чисел, дат, наименований |
| `parser/parse.py` | сборка результата и замечания |
| `parser/vision.py` | вторая ступень (vision-модель), выключена по умолчанию |
| `parser/cli.py` | командный интерфейс |

### 5.1. Единый вид данных

`read_cells()` отдаёт **строки документа с координатами X** — одинаково
для PDF и для скана. Это и есть главное архитектурное решение части 2:
вся разборка полей, разделение колонок и проверки написаны один раз
и работают независимо от источника текста.

Движки чтения PDF (`_dostupnye()` перебирает по порядку):

1. **pdfplumber** — основной, MIT;
2. **pymupdf** — если установлен, быстрее, но AGPL, поэтому не по умолчанию;
3. **pdftotext** (poppler, режим `-layout`) — запасной, координат не даёт,
   каждая строка становится одной ячейкой.

Три приёма при чтении PDF:

- **строки по координате Y** (допуск `ROW_TOLERANCE = 3.0` пункта), а не как
  есть: при плоском извлечении колонка с итогами разъезжается и подписи
  «Итого / В том числе НДС / Всего к оплате» уходят от своих чисел;
- **пробелы нулевой ширины выбрасываются**: часть генераторов PDF печатает
  их между буквами, и «ОБЩЕСТВО» приезжает как «ОБЩ ЕСТВО». Ложный пробел
  отличается измеримо — он уже `FAKE_SPACE_RATIO = 0.2` от кегля;
- **широкий разрыв рвёт ячейку**, даже если пробела в тексте нет
  (`GAP_RATIO = 0.8` кегля): иначе соседние колонки слипаются в одно слово.

Пустой результат на PDF — это скан: `ExtractionError` с прямым текстом
«в файле нет текстового слоя — это скан, нужен OCR».

### 5.2. Разбор полей

`fields.py` — набор регулярных выражений и правил, `parse.py` — сборка.

**Колонки.** Часть счетов свёрстана в две колонки: слева продавец, справа
покупатель. Если их не разделить, ИНН покупателя попадёт в реквизиты
получателя платежа и деньги уйдут не туда. Граница ищется по координате X
метки «Покупатель», реквизиты получателя берутся **только из левой колонки**.

**Поля.** Заголовок «Счёт на оплату № … от …», БИК, счета (корреспондентский
отличается префиксом `301`), ИНН и КПП, наименование, суммы. Учтены реальные
особенности: подписи `ИНН КПП` в одной строке со значениями в следующей
(Т-Банк), «… БИК» в конце строки со значением ниже (АК БАРС, ОЗОН Банк),
счета вразрядку `40802 810 9 4971 0010144` (СберБизнес), сумма прописью
(Контур), «Итого: 16 000.0» с одним знаком (СБИС), адрес и индекс, приклеенные
к наименованию (Альфа-Банк, 1С), сумма в строке с получателем (Точка).

**Наименование.** Приоритет у строки «Поставщик:» — в шапке счёта регулярно
разъезжается кернинг, в строке поставщика нет. `looks_broken()` ловит
разъехавшееся («СО ВРЕМ ЕН Н Ы Й ДОМ») по числу односимвольных слов.
Наименование с двоеточием или скобками («(Исполнитель): Москва, пр-кт …»)
помечается **ошибкой, а не заметкой**: такое имя ушло бы в поле «Получатель»
платёжки, и банк вправе отклонить платёж за несовпадение имени.

**Итоговая сумма** напечатана в счёте обычно трижды («Итого», «Всего
к оплате», «на сумму»). Если одну распознало криво, выбирается та, что
больше НДС и даёт заявленную ставку.

**Чужие документы.** Акт или платёжка, попавшие в пачку счетов, называются
по имени («это акт, а не счёт на оплату»), а не восемью «не найдено».

**Кто получатель.** `recipient_kind()`: «Режим НО: НПД», «самозанятый»,
«плательщик НПД» → `self_employed`; ИНН 12 знаков без ИП/ООО в имени или
счёт 40817/40820 → `person`; «ИП» в начале имени целым словом → `ip`;
иначе `org`. Маркер «ИП» ищется только в начале и целым словом — «ИП» внутри
фамилии («АНТИПИНА») маркером не считается. У физлица отрезается приклеившийся
хвост с покупателем («СЕРГЕЕВА Н. Н. ИП Немцева А. А.») и отбрасывается
распознанный КПП.

### 5.3. Распознавание сканов и фото

`ocr.py`. Два локальных движка, оба отдают слова с координатами:

| Движок | Роль | Замечания |
|---|---|---|
| `Windows.Media.Ocr` | основной там, где есть Windows | ставить ничего не надо, вызов через `parser/win_ocr.ps1`; на эталоне 33 ключевых поля из 40 |
| Tesseract | второй движок и единственный вне Windows | Apache 2.0, режим `tsv`; 24 поля из 40 — тащит линии таблиц как `[` и `|` |

Порядок выбран по замеру, а не по предпочтениям. Русский язык в установщик
Tesseract не входит, поэтому `rus.traineddata` лежит в `2-raspoznavanie/tessdata/`
и передаётся движку явным путём: писать в `Program Files` без прав
администратора нельзя, а служба на сервере обычно работает под ограниченной
учётной записью.

**Движок передаётся аргументом, а не через переменную окружения** — документы
разбираются в несколько потоков, и общая переменная сделала бы выбор гонкой.

Что решено отдельно:

- **Фото увеличивается перед распознаванием.** Телефон отдаёт счёт как
  960×1280, в шапке кегль выходит в 8–10 пикселей, и оба движка читают «ьик»
  вместо «БИК». Картинка обесцвечивается и увеличивается до короткой стороны
  ~2500 px, но не более чем вчетверо.
- **Склейка строк по перекрытию полос**, а не по «Y с допуском»: подписи
  «В том числе НДС» и «Всего к оплате» идут вплотную, при грубом допуске
  сливаются, и НДС получается равен итогу.
- **Починка цифр** (`ocr_repair.py`): `54 ооо,оо` → `54 000,00`,
  `КПП S32101001` → `532101001`, `НДС S%` → `НДС 5%`, `NQ` → `№`. Замены
  делаются только там, где по смыслу обязаны стоять цифры — иначе «о»
  в названии превратится в ноль.
- **Подписи — подсказка, решают контрольные суммы.** «№» теряется,
  «Покупатель» приезжает как «Покупатеть», «ООО» как «000», «БИК» не читается
  вовсе. Поэтому метки допускают искажения, а **БИК опознаётся по ключам
  счетов**: под верным БИК сходятся контрольные ключи расчётного и корр. счёта.
  Название банка берётся из той клетки, где стоит БИК, даже если слово «банк»
  не прочиталось.

Порог уверенности слова `MIN_CONF = 30.0` намеренно низкий: лучше пропустить
кривую цифру в проверку контрольных сумм, чем выбросить её и получить
«поле не найдено» без объяснения.

### 5.4. Вторая ступень (vision-модель)

`vision.py`. Счёт, не прошедший контрольные суммы после локальных движков,
может уйти на распознавание vision-модели. Модель возвращает не строки
с координатами, а сразу поля счёта. **Проверки те же самые** — модель
ошибается иначе, чем OCR, но ловится так же.

Это **единственное место во всём проекте, где документ уходит за пределы
сервера**, поэтому ступень выключена по умолчанию и включается двумя
переменными: `PP_VISION=1` и `ANTHROPIC_API_KEY`. Платится только за те счета,
которые не осилил локальный движок.

### 5.5. На чём проверено

**PDF:** 52 реальных счёта из СБИС, 1С:Бухгалтерии, Т-Банка, Альфа-Банка,
Контура, Сбербанк-форм, платформы НПД ФНС. Разобран 51, контрольные суммы
сошлись у всех. 52-й — скан без текстового слоя, парсер честно говорит,

50 из 60 полей совпали буквально, расхождения только в написании наименований

заменяет знакомым написанием). Сами изображения в репозиторий не кладутся.

### 6.1. Жизненный цикл пачки

```
загрузка файлов ──► docs.status = pending, batches.status = processing
        │
        │  фоновый поток, ThreadPoolExecutor (по умолчанию 4)
        ▼
разбор каждого документа ──► razbor.razobrat()
        │                    + подстановка из справочника получателей
        │                    + контрольные суммы заново
        ▼                    ──► docs.status = ok | problem | failed
поиск дублей (когда разобраны все) ──► docs.included = 0 с пометкой
        ▼
batches.status = review ──► экран проверки, правка руками
        ▼
«Сформировать файл» ──► нумерация + генератор ──► batches.status = exported
```

Браузер освобождается сразу после загрузки: страница пачки сама обновляется,
пока файлы разбираются, её можно закрыть и вернуться позже.

**Пределы.** До 500 счетов в пачке (`PP_PREDEL_PACHKI`), 25 МБ на файл,
600 МБ на пачку (`PP_PREDEL_PACHKI_MB`). Предел в 500 стоит не из-за скорости
разбора, а из-за человека. Файл, не уложившийся в пределы, **не пропадает
молча**, а становится строкой со статусом `skipped` и объяснением, сколько
он весит: раньше он исчезал беззвучно, и бухгалтер грузил полсотни счетов,
получал сорок восемь и не мог понять, каких двух не хватает.

### 6.2. Две ступени и склейка полей

`razbor.py`. Схема:

```
файл ─► текстовый слой PDF или локальный OCR ─► контрольные суммы
     ├─ сошлось ──────────────────────────────► в пачку
     ├─ не сошлось ─► второй движок ─► склейка полей ─► те же проверки
     ├─ не сошлось и включена вторая ступень ─► vision ─► те же проверки
     └─ и там не сошлось ─► человеку, с указанием конкретных полей
```

**Проверки одни и те же на всех путях — это главное.**

Движки ошибаются по-разному: один теряет клетку с расчётным счётом, другой —
знак «№» в заголовке. Брать лучший разбор целиком значит терять то, что второй
прочитал верно. Поэтому поля **склеиваются** (`slit()`): за основу берётся
разбор с меньшим числом замечаний, а недостающее или не прошедшее контрольную
сумму добирается из другого — **только если там оно контрольную сумму
проходит**. В заметках к счёту видно, что и откуда взято.

БИК и счета берутся из другого движка только связкой: `_bank_shoditsya()`
требует, чтобы под БИК сошёлся ключ хотя бы одного из счетов.

**Замечания парсера и контрольные суммы хранятся раздельно** (`iz_parsera`
и `problems`). Контрольные суммы после подстановки из справочника
пересчитываются, а замечания парсера («счёт выставлен не нам», «не найден
БИК») должны пересчёт пережить. Однажды они терялись, и 49 чужих счетов ушли
в файл для банка как чистые. Таблица `ZAKRYVAETSYA` описывает, какое замечание
каким условием снимается после склейки.

### 6.3. Справочник получателей

`poluchateli.py`. Заполняется сам: каждый разобранный счёт добавляет получателя
и считает, сколько счетов от него было и сколько раз ему заплатили. Ключ —
**(компания, ИНН, счёт)**, а не просто ИНН: у одного контрагента законно бывает
несколько счетов, схлопывать их нельзя.

**Что справочник вправе дописать:** КПП, город банка, название банка,
корр. счёт, полное наименование — и только в пустое поле. Распознанное
никогда не затирается, подстановка всегда помечается заметкой на экране.

**Чего он не подставляет никогда:** расчётный счёт, ИНН, БИК. Это то, по чему
уходят деньги; брать их из истории вместо документа — значит платить
по вчерашним реквизитам.

**Единственное поле, которое справочник вправе заменить,** — наименование,
и только когда стоит флаг `_name_unreliable`. Со скана оно регулярно приезжает
мусором («(Иттолнитель): Москва, пр-кт…») при верных ИНН и счёте; раз по этим
реквизитам уже платили, имя известно точно. Пока не платили — счёт идёт
человеку.

**НДС из истории.** Счёт с `vat_status = unknown` не идёт человеку с вопросом,
если по прошлым счетам известно «без НДС» или ставка: значение подставляется
с заметкой, для ставки сумма НДС считается от итога
(`итог × ставка / (100 + ставка)`, округление half-up). На экране проверки
ставка выбирается из списка («Без НДС», 22, 20, 10, 7, 5 %), выбор запоминается
за получателем. **Счёт с неопределённым НДС в файл не уходит.**

Хранится **последнее известное** значение НДС (получатель мог перейти на УСН
или стать плательщиком НДС), а неопределённость не затирает известное.
Остальные поля наоборот: справочник накапливает, а не переписывается последним
счётом.

`dvoyniki()` помечает ИНН, у которых в справочнике больше одного расчётного
счёта. Обычно это законно, но смена реквизитов «в письме от контрагента» —
классическая схема мошенничества, и такой случай стоит проверить звонком.

### 6.4. Дубли

Один счёт — одна платёжка. Ключ дубля (`_kluch_scheta`): получатель, его
расчётный счёт, номер и дата счёта, сумма. Проверяются два случая:

- **дважды в одной пачке** — счёт отсканировали повторно, прислали и почтой,
  и в мессенджере;
- **уже выгружался раньше** — по журналу нумерации (`already_paid`).

Такие документы не удаляются, а исключаются из выгрузки (`included = 0`)
с пометкой: решает человек, вдруг это два разных счёта с совпавшими
реквизитами. Вернуть в пачку — одна кнопка.

### 6.5. Плательщик по счетам

`pokupatel_pachki()`. Пачку легко загрузить не под той организацией.
Сервис считает, чей ИНН стоит в графе «Покупатель» чаще всего; если чужих
больше, чем своих, предлагает:

- **переназначить пачку** одной кнопкой, если такой плательщик заведён;
- **завести плательщика**, если его нет: форма открывается с заполненными
  наименованием, ИНН и КПП, взятыми по большинству из счетов.

После переназначения **пачка разбирается заново целиком**: замечания
«выставлен не нам», проверка дублей и подстановки из справочника зависят
от того, кто платит. Дешевле перечитать сорок сканов, чем вычищать эти следы
по одному.

Один чужой счёт среди своих предложения не вызывает — это отдельный счёт,
а не ошибка пачки.

### 6.6. Плательщики и их счета

У организации-плательщика может быть несколько расчётных счетов («в Точке»,
«в Сбербанке») — это **один плательщик и два счёта** (`payers` и
`payer_accounts`). При загрузке пачки выбирается, с какого платить.

Для генератора эти счета остаются разными плательщиками (`payer_iz_stroki()`
склеивает строку организации со строкой счёта), и это правильно: ключ счётчика
номеров включает номер счёта, нумерация в банках независимая. Начальные номера
у счетов лучше развести (900001 и 800001), чтобы по номеру платёжки было видно,
из какого банка она ушла.

### 6.7. Реквизиты плательщика из старой платёжки

`iz_platezhki.py` — 744 строки, самый плотный модуль сервиса. Набивать
двадцатизначный счёт руками — ровно тот случай, где опечатка тихо проходит
глазами и всплывает в банке.

Два вида источника:

1. **файл обмена** `1CClientBankExchange` (`1c_to_kl.txt` — выгрузка из 1С,
   `kl_to_1c.txt` — выписка из банка): точный источник, реквизиты лежат
   готовыми полями;
2. **платёжное поручение** в PDF или снимком — разбирается как счёт.

Результат **не сохраняется сам**: он проверяется контрольными суммами
и показывается человеку в форме. Сохраняет человек.

Три решения, которые пришлось принять:

**В платёжке две стороны, и ваша может быть любой.** В своей исходящей
платёжке организация — плательщик. Но подтверждение поступления, которое
выгружают из банка (так делает Альфа-Банк), — это платёжка, где вы
*получатель*. Поэтому читаются обе стороны, а какая ваша — решается
по признакам: в файле обмена это счёт из шапки (`РасчСчет`), в PDF — банк,
выдавший документ (его БИК стоит в отметках внизу и совпадает с банком одной
из сторон). Признаков нет — берётся плательщик, а вторая сторона доступна
кнопкой «Это не мы — взять …» без повторного чтения файла.

**Подпись клетки — только подсказка, решают контрольные суммы.** Искать
значение рядом с подписью можно, только если они рядом стоят, а в бланке
0401060 это не так: номера печатают вразрядку по клеткам
(`6 1 6 1 2 5 8 5 5 3 2 6`), подпись «ИНН» уезжает в свою строку, соседние
клетки слипаются. Поэтому реквизит опознаётся по себе самому — у ИНН, БИК
и счетов есть контрольные суммы.

**БИК выбирается не первым подходящим**, а тем, под которым сходятся ключи
расчётного и корр. счетов: девять цифр сходятся у слишком многих чисел,
в том числе у начала ИНН.

Мелочь, которая стоила ошибки: **длина ИНН проверяется сначала 12, потом 10** —
иначе от ИНН предпринимателя откусывались бы первые десять цифр.

### 6.8. Что человек правит на экране проверки

Поля из кортежа `POLYA` в `pachki.py`: номер и дата счёта, наименование
(краткое и полное), ИНН, КПП, счёт, банк и город, БИК, корр. счёт, сумма,
сумма НДС, «за что платим». Ставка НДС — выбор из списка, а не поле ввода.

После правки данные **проверяются заново** тем же `proverit_summy()`.
Счёт, который парсер не осилил, а человек поправил, попадает в справочник
получателей — это тоже знание о контрагенте.

Под полем «За что платим» показано назначение платежа целиком и его длина —
ровно то, что уйдёт в файл.

## 7. База данных

SQLite, файл `servis/dannye/servis.db`, режим WAL, внешние ключи включены.

Почему не Postgres: сервис ставится на сервер организации, пачек в день —
десятки, а не тысячи. Один файл проще администрировать и бэкапить,
а транзакции нужны ровно в одном месте (выдача номеров), и их SQLite даёт
честно. Переход на Postgres, если понадобится, затронет один файл `db.py`.

**Мультиарендность заложена с первого дня:** `company_id` есть в каждой
таблице с данными. Прикрутить её потом, когда в базе уже лежат чужие платежи,
нельзя.

| Таблица | Что хранит |
|---|---|
| `companies` | организация-арендатор |
| `users` | пользователи, роль `operator` / `buhgalter` / `admin`, scrypt-хеш пароля |
| `sessions` | сессии (в базе, не в подписанной куке) |
| `payers` | плательщик: код, наименование, ИНН, КПП |
| `payer_accounts` | расчётный счёт плательщика: метка, реквизиты банка, `numbering_start`, профиль банка |
| `poluchateli` | справочник получателей, ключ (компания, ИНН, счёт), счётчики и НДС |
| `batches` | пачка: плательщик, счёт, статус, дата платежа, имя выгрузки |
| `docs` | документ в пачке: имя, статус, движок, `data_json`, `problems_json`, `included` |
| `counters` | счётчик номеров, ключ (компания, `плательщик\|счёт\|год`) |
| `assigned` | номер, закреплённый за счётом (`identity` → номер + payload) |
| `exports` | факт выгрузки: файл, номера, сумма |
| `audit` | кто что делал — речь о платежах, поэтому пишется всё |
| `popytki` | попытки входа для защиты от подбора |

**Транзакции.** `db.transaction()` открывает `BEGIN IMMEDIATE` — блокировка
на запись берётся сразу, а не при первой записи: два сотрудника, нажавшие
«Сформировать» одновременно, не получат один и тот же номер.

**Соединение на запрос**, `check_same_thread=False`: FastAPI выполняет обычные
(не async) обработчики в пуле потоков, и соединение, созданное зависимостью,
попадает в обработчик уже в другом потоке. Соединение живёт один запрос
и используется строго по очереди. Фоновый разбор открывает своё соединение
на каждый документ.

**Миграция схемы** — `dovesti_shemu()`, вызывается при каждом старте.
Реализованы два перехода: расчётный счёт из строки плательщика в отдельную
таблицу (с переносом данных и привязкой старых пачек) и добавление полей НДС
в справочник получателей. Столбцы, которые старый SQLite не умеет удалять,
остаются лежать неиспользуемыми.

## 9. Безопасность

**Пароли** — scrypt из стандартной библиотеки (`n=2^14, r=8, p=1`, соль
16 байт, ключ 32 байта). Отдельная библиотека не нужна, а меньше зависимостей —
меньше поводов не обновиться. Минимальная длина 8 знаков.

**Сессии живут в базе**, а не в подписанной куке: администратор может выкинуть
уволенного сотрудника немедленно. Срок 12 дней, кука `httponly`,
`samesite=strict` и `secure` при HTTPS.

**Сервис нельзя выставлять в интернет по голому HTTP.** Через него ходят пароли
и банковские реквизиты, а кука `secure` по HTTP браузером не возвращается —
войти физически не получится. Перед сервисом ставится обратный прокси
с сертификатом (Caddy, nginx, IIS+ARR), сам сервис слушает только `127.0.0.1`.

**Защита форм от подделки** (CSRF): скрытый токен — HMAC-SHA256 от токена
сессии на ключе `dannye/sekret.key`, сравнение постоянным по времени
(`compare_digest`). Ключ создаётся при первом запуске и больше не меняется.

**Защита от подбора пароля**: скользящее окно 15 минут, 5 неудач по логину
и 20 по адресу закрывают вход. После удачного входа счётчик обнуляется —
иначе пять опечаток за день закрывают вход человеку, который в итоге вспомнил
пароль. Записи о попытках хранятся 7 суток.

Пароль проверяется **даже для несуществующего логина** (сравнение с фиктивным
хешем): иначе по времени ответа видно, какие логины в системе есть.

**Настоящий адрес за прокси** берётся из `X-Forwarded-For`, но **только если
запрос пришёл с этой же машины**, то есть от нашего прокси. Иначе адрес можно
было бы подделать и обнулять себе счётчик попыток на каждом запросе.

**Разделение организаций**: каждый запрос фильтруется по `company_id`
пользователя. Пачка чужой компании отвечает 404, а не 403.

**Имена файлов** приводятся к безопасным (`_bezopasnoe_imya`), на диске
хранятся под случайным именем (`secrets.token_hex(8)` + расширение), исходное
имя — в базе.

**Первый запуск работает ровно один раз**: как только в базе появился
пользователь, страница `/nachalo` отдаёт на обычный вход — иначе на работающем
сервисе любой прохожий сделал бы себя администратором.

## 11. Запуск и развёртывание

### Локально

```bat
zapusk.bat
```

Окно с тремя кнопками («Запустить», «Открыть в браузере», «Остановить»),
консоли нет. Порт подбирается свободный начиная с 8000 (до 20 подряд):
занятый порт — обычное дело, и падать с «address already in use» человеку,
который просто дважды щёлкнул по значку, нельзя. Логика запуска отделена
от окна (`servis/zapuskator.py`) и покрыта тестами; окно (`zapusk.pyw`) тонкое.

Из командной строки:

```bat
pip install -r servis\requirements.txt
python -m servis
```

### На сервер

Пошаговая инструкция — [razvertyvanie/README.md](razvertyvanie/README.md),
скрипты `sobrat.ps1` (собрать архив на своей машине, рабочие данные в него
не попадают) и `ustanovka.ps1` (установка на сервере, повторный запуск
пропускает уже сделанное).

Выбрано и почему:

| | Решение | Почему |
|---|---|---|
| Площадка | VPS с **Windows Server** у российского хостера | на Windows работает встроенный OCR — основной движок для сканов; на Linux остался бы только Tesseract |
| HTTPS | Caddy + Let's Encrypt | обязателен: кука `secure` по HTTP не возвращается |
| Служба | NSSM, служба `SchetaVBank` | поднимается сама после перезагрузки |
| База | SQLite как есть | десятки пачек в день, один файл проще бэкапить |

Ставятся Python (PSF), Tesseract (Apache 2.0), NSSM (public domain),
Caddy (Apache 2.0) — AGPL нет ни в одном.

**После обновления кода службу надо перезапустить** (`Restart-Service
SchetaVBank`), иначе люди продолжат видеть старое поведение. То же и локально:
закрыть окно и запустить `zapusk.bat` заново.

### Резервные копии

Всё нужное — в `servis/dannye`: `servis.db` (пользователи, плательщики,
**журнал нумерации**, аудит), `sekret.key`, `zagruzki/`, `vygruzki/`.
Копировать базу лучше средствами SQLite (`.backup`), а не копированием файла.

**Потеря журнала нумерации означает, что счётчик начнётся заново и в банк
уйдут платёжки с уже использованными номерами.**

Ночное задание `Scheta-kopiya` кладёт копию в `C:\pp-bank\kopii` (база каждую
ночь, исходные счета по воскресеньям, храним 14 копий). Копия на том же
сервере — это полумера, раз в неделю папку надо уносить наружу.

строки в них взяты с реальных счетов, но сами PDF не нужны.

по клеткам, подписи оторваны от значений. **Тест сначала убеждается, что
образец воспроизводит поломку, и только потом проверяет разбор** — иначе
образец ничего не стоит. Пересоздать: `python servis/tests/obraztsy/sdelat.py`
(pymupdf нужен только для изготовления образцов, в поставку он не входит).

## 14. Часть 3 — загрузка в 1С (не реализована)

Каталог `3-zagruzka-v-1c/`, пока только разбор каналов —

отдельный служебный пользователь с минимальными правами.

## 15. Известные ограничения

**1. Файл ни разу не принят живым клиент-банком.** Формат собран
по спецификации, разобран построчно и покрыт тестами, но проверки на настоящем
банке не было. Единственная попытка (сентябрь 2026) дала список ошибок банка,
который **с нашим файлом не совпадает** — ни номера, ни ИНН, ни счета из него
в файле не встречаются; вероятно, в банк ушёл другой файл. Пока это
не выяснено, формат считается непроверенным. Чек-лист того, что надо
проверить на живом банке, — п. 8
[FORMAT-1CClientBankExchange.md](1-vygruzka-v-bank/FORMAT-1CClientBankExchange.md).

**2. PDF-скан (скан, сохранённый в PDF) в OCR не попадает.** Известная дыра:
если у PDF нет текстового слоя, парсер честно советует сохранить счёт
картинкой, но сам его не распознаёт. Мостик «PDF → изображение → OCR»
не сделан.

**3. Наименование получателя со скана регулярно приезжает мусором** при верных
ИНН и счёте. Это помечается ошибкой (иначе мусор уйдёт в поле «Получатель»),
и это единственное поле, которое справочник получателей вправе заменить.
Для незнакомого получателя счёт идёт человеку.

**4. Старые загрузки не чистятся.** Исходные счета копятся в
`servis/dannye/zagruzki/` без ограничения по сроку.

**5. Слой 2б (позиции и номенклатура) не реализован.** Для платёжек не нужен,
понадобится для части 3.

**6. Копия базы кладётся на тот же сервер.** Унос наружу — ручная процедура.
