# Разбор сервиса helper-buh.ru (страница /upload-payment-orders)

Дата разбора: 2026-08-26. Источник: публичная страница + публичные JS-бандлы сайта.

## Что это

Next.js-приложение. Позиционирование в мета-тегах: «XML для 1С из PDF, сканов и фото»,
«распознаёт данные с точностью до 99,5%». Страница `/upload-payment-orders` — отдельный
сценарий: счета → платёжные поручения → TXT для клиент-банка.

## Поток работы (5 шагов)

1. **Реквизиты плательщика.** Блок «Реквизиты плательщика»: сохранённые «счета плательщика»
   в личном кабинете, выбор счёта из списка. Есть автоподбор — флаг `payment_account_auto_matched`
   («Определено автоматически»), т.е. сервис пытается сам понять, с какого счёта платить.
2. **Загрузка пачки счетов.** Drag-and-drop, «Перетащите файлы сюда или выберите несколько»,
   «Пакетная загрузка до 30 счетов». Форматы: `.pdf, .jpg, .jpeg, .png`.
   Лимит: 30 файлов гостю / 50 авторизованному.
3. **Распознавание.** Асинхронное, с опросом статуса: `pending → processing → completed / failed / error`.
   В UI — «Обрабатываем гостевой пакет…», «Загрузка статуса обработки…».
4. **Проверка и правка.** Таблица «Счета по группам», каждое поле редактируется вручную
   (все поля в UI — controlled inputs, т.е. распознанное можно поправить до выгрузки).
5. **Выгрузка.** Кнопки «Сформировать TXT для банка», «Скачать TXT (платежка)», «Скачать платежку».

## Модель данных (имена полей из бандла)

Плательщик (сохранённый счёт):
`payer_name`, `payer_full`, `payer_inn`, `payer_account`,
`payer_bank_name`, `payer_bank_city`, `payer_bic`, `payer_corr_account`

Получатель (распознаётся из счёта):
`recipient_name`, `recipient_full`, `recipient_inn`, `recipient_account`,
`recipient_bank_name`, `recipient_bank_city`, `recipient_bic`, `recipient_corr_account`

Платёж:
`total_amount` / `total_amount_str`, `vat_rate` / `vat_rate_str`, `vat_amount` / `vat_amount_str`,
`payment_purpose`

Пара «число + строка» (`total_amount` + `total_amount_str`) — приём, чтобы хранить и разобранное
число, и то, что реально написано в счёте, и не терять исходник при кривом распознавании.

## API (по вызовам из фронтенда)

| Метод/путь | Назначение |
|---|---|
| `POST /api/invoice/public/create_from_files_batch` | гостевая пачка (без регистрации) |
| `POST /api/invoice/invoices/create_from_files_batch` | пачка для авторизованного |
| `GET  /api/invoice/groups` | список групп (пачек) счетов |
| `GET  /api/invoice/payment_accounts` | сохранённые счета плательщика |
| `PATCH/PUT /api/invoice/invoices/{id}` | правка распознанного счёта |
| `PUT  /api/invoice/groups/{id}/payment_account` | привязать счёт плательщика к группе |
| `GET  /api/invoice/groups/{id}/client_bank_export` | **выгрузка TXT для клиент-банка** |
| `GET  /api/documents/{id}/status` | статус обработки документа |

## Ключевая архитектурная идея

Единица работы — **группа (пачка)**, а не отдельный счёт. Один счёт плательщика на группу,
внутри — N счетов от разных поставщиков, на выходе — **один TXT со всеми платёжками**.
Это и есть то, что экономит время бухгалтеру.

## Чего не видно снаружи

- Формат TXT генерируется на сервере — точную структуру из фронтенда не достать.
  Почти наверняка это стандартный `1CClientBankExchange` (кодировка windows-1251,
  секции `СекцияДокумент=Платежное поручение`). **Требует проверки на реальном клиент-банке.**
- Чем распознаёт (какая OCR/LLM-модель) — не видно.
- Как считает НДС при расхождении «в т.ч. НДС» и ставки — не видно.
- Цены на этой странице нет; в мета-тегах — «1000 ₽ на баланс после регистрации».
