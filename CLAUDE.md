# Счета-платёжки

Сервис: на вход счета от заказчиков, на выходе — файл платёжных поручений для клиент-банка.

**Направление продукта:** не «под мои банки», а универсальный инструмент, пригодный
для передачи сторонним организациям. Значит: любой банк, любая организация-плательщик,
никаких зашитых реквизитов в коде.

## Две части проекта

### Часть 1 — выгрузка в банк (`1-vygruzka-v-bank/`)
Формирование файла для клиент-банка. Основа — открытый стандарт `1CClientBankExchange`
(формат «из 1С в банк», файл `1c_to_kl.txt`). Спецификация разобрана по пунктам:
[FORMAT-1CClientBankExchange.md](1-vygruzka-v-bank/FORMAT-1CClientBankExchange.md).

Универсальность = одно ядро генератора + тонкие профили банков в `profili-bankov/`
(версия формата, кодировка, мелкие придирки конкретного банка).

**Статус: реализовано и покрыто тестами.** Запуск и описание — [README](1-vygruzka-v-bank/README.md).
Нумерация платёжек — [RESHENIE-numeratsiya.md](1-vygruzka-v-bank/RESHENIE-numeratsiya.md).
**На живом клиент-банке файл до сих пор не подтверждён.** Единственная попытка
(сентябрь 2026) дала список ошибок банка, который с нашим файлом не совпадает —
ни номера, ни ИНН, ни счета из него в файле не встречаются; вероятно, в банк ушёл
другой файл. Пока это не выяснено, считать формат непроверенным
(чек-лист в спецификации, п. 8).

Эта часть **не зависит** от распознавания: на вход ей идёт структура данных, откуда
она взялась — неважно. Её можно делать и тестировать первой.

### Часть 2 — распознавание счетов (`2-raspoznavanie/`)
Извлечение данных из счетов в разных форматах (PDF, скан, фото, Excel).
Делится на два слоя, [NOMENKLATURA.md](2-raspoznavanie/NOMENKLATURA.md):

- **2а, шапка** — реквизиты получателя, номер и дата счёта, сумма, НДС.
  Этого достаточно для части 1: в платёжке нет табличной части.
  **Статус: реализовано**, [README](2-raspoznavanie/README.md). Проверено на 52 реальных
  счетах: СБИС, 1С, Т-Банк, Альфа-Банк, Контур, платформа НПД ФНС. Разобран 51,
  контрольные суммы сошлись у всех; 52-й — скан без текстового слоя, помечен как
  требующий OCR. Работает по текстовому слою PDF, без OCR и без модели.
- **2в, сканы** — распознавание счетов-картинок. **Первая ступень готова:**
  два локальных движка. Встроенный `Windows.Media.Ocr` — основной (на эталоне
  33 ключевых поля из 40), Tesseract — второй (24 из 40, спотыкается о рамки
  таблиц) и единственный вне Windows; русский язык для него лежит в
  `2-raspoznavanie/tessdata/`, в Program Files не пишем. Счёт, не сошедшийся
  у первого движка, перепроверяется вторым; движок передаётся аргументом, не через
  окружение (разбор идёт в несколько потоков). Эталон — `2-raspoznavanie/etalon/`:
  три скана из четырёх чисто, четвёртый (тёмная полоса) — только vision-модели.
  **PDF без текстового слоя (скан, сохранённый в PDF) в OCR пока не попадает** —
  известная дыра, сервис честно советует сохранить картинкой.
  Наименование получателя со скана регулярно приезжает мусором при верных ИНН
  и счёте: это ошибка, а не заметка (иначе мусор уходит в поле «Получатель»),
  и единственное поле, которое справочник получателей вправе заменить.
- **2б, позиции** — товарные строки и сопоставление с номенклатурой 1С.
  Нужно только для части 3. Сопоставление накапливается: человек подтверждает
  один раз, дальше автоматически. Автосоздание номенклатуры по умолчанию выключено.

### Часть 3 — загрузка в 1С (`3-zagruzka-v-1c/`)
Заведение распознанных счетов в 1С как документов. Разбор каналов —
[ISSLEDOVANIE.md](3-zagruzka-v-1c/ISSLEDOVANIE.md). Утверждённого XML-формата
для счёта на оплату не существует, поэтому выбираем канал, а не формат:
OData (прямая запись в базу, у 42Clouds включён по умолчанию) либо EnterpriseData
(XML в папку обмена, 1С забирает по расписанию).

Питается тем же контрактом, что и часть 1: один источник данных, два выхода.

## Контракт между частями

Часть 2 отдаёт, часть 1 принимает (имена полей — по разбору аналога):
получатель: `recipient_name`, `recipient_full`, `recipient_inn`, `recipient_kpp`,
`recipient_account`, `recipient_bank_name`, `recipient_bank_city`, `recipient_bic`,
`recipient_corr_account`;
платёж: `invoice_number`, `invoice_date`, `total_amount`, `vat_rate`, `vat_amount`,
`vat_status`, `payment_purpose`, `payment_description`.

`payment_description` — за что платим: наименования позиций счёта через «; »,
без цен и количеств. Генератор собирает из них назначение платежа
(«Оплата по счету № N от Д за <позиции>. В т.ч. НДС …») и ужимает описание
в предел банка (210 знаков) так, чтобы хвост про НДС уцелел: у одинаковых
позиций берётся общее начало («заправка картриджа Kyocera (6 позиций)»),
иначе перечисляется сколько влезло и «и др.». Готовый текст в `payment_purpose`
имеет приоритет.

`recipient_kind` — кто получатель: `org` / `ip` / `self_employed` / `person`.
Физлицу (самозанятому в том числе) генератор ставит код вида дохода `1`
в поле 20 (`КодНазПлатежа`) и не пишет КПП; ИП и организациям поле пустое.
Признаки и банковские правила — [PRAVILA-samozanyatye.md](PRAVILA-samozanyatye.md).

Служебные поля с подчёркиванием (`_buyer_inn`, `_buyer_name`, `_buyer_kpp`)
в платёжку не идут: по ним сервис узнаёт, на кого выставлен счёт.

`vat_status`: `included` — НДС выделен; `none` — в счёте написано «Без НДС»;
`unknown` — не нашли и про отсутствие не сказано, счёт идёт на проверку человеку.
Без этого различия бухгалтер получает предупреждение на каждом счёте ИП на УСН.

Каждая распознанная сумма хранится парой: число + исходная строка из счёта
(`total_amount` / `total_amount_str`), чтобы не терять оригинал при ошибке распознавания.

### Часть 4 — сервис (`servis/`)
Оболочка над частями 1 и 2: веб-интерфейс, в который сотрудники загружают счета
и забирают файл для клиент-банка. Ставится на сервер организации, вход по логину
и паролю, три роли: «оператор» (грузит счета и забирает файл), «бухгалтер»
(плюс справочники — плательщики, их счета, получатели) и «администратор»
(плюс сотрудники и пароли). Роль меняет администратор на странице
«Сотрудники»; себе — не может, вернуть её было бы некому.

Логику частей 1 и 2 сервис **не дублирует, а вызывает** — правила формата,
проверки реквизитов и нумерация остаются в одном месте. Заменено ровно два узла:
журнал нумерации переехал из файла в базу (на сервере сотрудников несколько,
и два одновременных нажатия «Сформировать» обязаны получить разные номера),
а справочники плательщиков — из JSON-файлов в справочник интерфейса.

У организации-плательщика может быть несколько расчётных счетов: «ТЕТРАКОМ в Точке»
и «ТЕТРАКОМ в Сбербанке» — это один плательщик и два счёта. Для генератора они
остаются разными плательщиками, и это правильно: ключ счётчика номеров включает
номер счёта, нумерация в банках независимая.

Справочник получателей набирается сам из разобранных счетов. Из него дописываются
только поля, которые не адресуют деньги (КПП, город и название банка, корр. счёт).
Расчётный счёт, ИНН и БИК берутся исключительно из документа — брать их из истории
значит платить по вчерашним реквизитам.

Справочник помнит и НДС получателя. Счёт, который про НДС молчит
(`vat_status = unknown`), не идёт человеку с вопросом, если по прошлым счетам
известно «без НДС» или ставка: значение подставляется с заметкой, а на экране
проверки ставка выбирается из списка («Без НДС», 22, 20, 10, 7, 5 %). Выбор
бухгалтера запоминается за получателем. Без выбора счёт с неизвестным НДС
в файл не уходит.

Плательщик определяется по счетам, а не наоборот: если большинство счетов
пачки выставлены на другую организацию, сервис предлагает переназначить пачку
на неё одной кнопкой (если такой плательщик заведён) либо завести его
с уже заполненными наименованием, ИНН и КПП. После переназначения пачка
разбирается заново — замечания «выставлен не нам», дубли и подстановки
зависят от того, кто платит.

Реквизиты плательщика заводятся из его документа — платёжки, выписки, файла
обмена или счёта (из счёта только «кто платит»: банковских реквизитов плательщика
в счёте не печатают). Бланк 0401060 читается **по контрольным суммам, а не по
подписям клеток**: цифры печатают вразрядку по клеткам, подписи уезжают в другие
строки, приклеиваются к числам без пробела. БИК — тот, под которым сходятся ключи
обоих счетов, потому что одиночная проверка БИК слабая. Разбор проверяется на
трёх настоящих PDF в `servis/tests/obraztsy/` (генератор — `sdelat.py`, pymupdf
только для изготовления, не в поставке).

Замечания парсера («счёт выставлен не нам», «не найден БИК») и контрольные суммы
хранятся раздельно и оба доходят до экрана: однажды первые терялись при пересчёте,
и 49 чужих счетов ушли в файл как чистые.

**Статус: работает,** [README](servis/README.md). Разделение организаций заложено
в схему базы с первого дня: `company_id` есть в каждой таблице с данными.
Запуск — `zapusk.bat` (окно с кнопками, первый вход в браузере, консоли нет);
организацию при регистрации не спрашиваем — плательщика и банк бухгалтер выбирает
в момент платежа.

## Структура

- `1-vygruzka-v-bank/` — формат и генератор файла для банка
  - `profili-bankov/` — настройки под конкретные банки
  - `platezhki/` — готовые выгрузки
- `2-raspoznavanie/` — распознавание счетов
  - `parser/` — разбор PDF
  - `scheta/` — входящие счета
- `konveyer.py` — сквозной прогон: папка со счетами → файл для банка
- `PRAVILA-samozanyatye.md` — платёжки самозанятым и физлицам: поле 20, КПП, признаки в счёте
- `3-zagruzka-v-1c/` — заведение счетов в 1С (OData / EnterpriseData)
- `servis/` — веб-сервис поверх частей 1 и 2
  - `app/` — приложение: база, вход, пачки, справочники
  - `dannye/` — база, загруженные счета, выгрузки (в репозиторий не кладутся)
  - `tests/obraztsy/` — настоящие PDF-платёжки для сквозных проверок
  - `zapuskator.py` — запуск/остановка сервиса без консоли (тестируется)
- `zapusk.bat`, `zapusk.pyw` — окно запуска для пользователя
- `spravochniki/` — реквизиты плательщиков, шаблоны, аналитика рынка

## Как работать с проектом в новой сессии

- **Тесты — три набора, все должны быть зелёными** (на 2026-09-05: 44 + 79 + 86):
  `python -m unittest discover -s 1-vygruzka-v-bank/tests`,
  `… -s 2-raspoznavanie/tests`, `cd servis && python -X utf8 -m unittest discover -s tests`.
  Сервисные тесты подменяют базу и папки на временные, рабочие данные не трогают.
- **Пользователь работает в запущенной программе.** После любой правки кода ей
  нужно закрыть окно и запустить `zapusk.bat` заново — иначе она видит старое
  поведение и пишет «ничего не изменилось». Напоминать об этом в ответе.
- **Файлы из чата не всегда доезжают на диск.** Если файла нет — не чинить по
  догадке, а просить положить его в `C:\Projects\pp-bank` или прислать текст из
  блока «что программа прочитала в документе» на странице плательщиков.
- Настоящие данные для проверки: её загрузки лежат в `servis/dannye/zagruzki/`,
  результат разбора — в `servis/dannye/servis.db` (таблица `docs`). Смотреть
  туда раньше, чем рассуждать.
- Рабочая база — её данные. Не удалять, не переименовывать, не чинить записи
  без вопроса.
- Внешнее (скилы, пакеты, установщики) — только после явного одобрения.
- Пользователь диктует голосом: имена в сообщениях искажены («Тотраком»,
  «Tetracomi»), восстанавливать по смыслу.

## Открытые вопросы (2026-09-05)

- Файл ни разу не принят живым клиент-банком; список ошибок банка с нашим файлом
  не совпадает — выяснить, что именно загружалось.
- Плательщик-организация, на которую выставлено большинство тестовых счетов,
  в справочнике ещё не заведён; последняя пачка загружена под другим плательщиком,
  и 44 счёта из 51 честно помечены «выставлен не нам». Перезагрузить под нужным.
- Предложено, ждёт решения: плательщик по счетам с переназначением пачки одной
  кнопкой; режим НДС из истории получателя (а не «нет НДС → Без НДС», это опасно
  для вычета); настраиваемый шаблон назначения платежа; OCR для PDF-сканов;
  включение vision-ступени для нечитаемых сканов (платно, документ уходит наружу).

## Договорённости

- Ничего не уходит в банк автоматически: итог работы — файл, загружает его человек.
- Суммы, ИНН, КПП, БИК, номера счетов не додумываем: нет или нечитаемо — спрашиваем.
- Реквизиты плательщика — данные, а не код. Никаких конкретных организаций в исходниках.
- Никаких AGPL-зависимостей: инструмент отдаётся сторонним организациям, а AGPL
  распространяется и на доступ по сети. Поэтому PDF читает pdfplumber (MIT),
  а не PyMuPDF.
- Документ уходит за пределы сервера ровно в одном месте — вторая ступень
  распознавания. Она выключена по умолчанию и включается настройкой.
